Why It Kept Falling Over

Four unrelated production incidents in four days — an unbounded cache that grew until the process died, an index that quietly pointed at the wrong volume, a stampede against a cache that had never once been cleaned, and corrupted files straight from NOAA. None of it visible in a screenshot. All of it the difference between the app working and not.

Why this one's worth writing up

Most of what gets written up here is about what the radar shows and why. This post is about what keeps it showing anything at all. Over a four-day stretch, four separate incidents took the server down or degraded it — none of them related to each other, none of them visible to anyone just looking at a rendered tile. They're worth a post of their own because the pattern across all four is the same one: something was allowed to grow, or repeat, or be trusted, without a limit on it.

Incident one: a cache that grew until the process died

Production memory climbed to a 3.1 GB peak, and every so often the process silently restarted — a V8 out-of-memory kill, not a crash with a stack trace pointing anywhere useful.

The cause: two render caches (tierRenderCache, overlayTierRenderCache) were plain JavaScript Map objects with no eviction. Every unique combination of volume, zoom tier, and pan offset got its own permanent entry. A busy day of panning and zooming across several stations just kept adding entries, forever, until the heap gave out.

Fixed by swapping both for a bounded LRU cache capped at 300 entries. Memory stabilized at roughly 220 MB on a fresh restart — down from a 3.1 GB peak that used to recur every few days.

Incident two: auto-refresh that quietly stopped updating

Three separate tester reports, at first glance unrelated: auto-refresh freezing, auto-refresh stalling, and a brand-new page load occasionally showing an old frame labelled as the latest one. All three turned out to be the same bug.

Every tile route (/frames/:index/tile and its batch/overlay variants) identified a frame by its array position in the server's rolling window of recent scans. That window recomputes every five seconds, and a background prewarm loop recomputes it independently on its own schedule. So "frame 3" in the metadata the browser just received could resolve to a completely different volume by the time a follow-up tile request for "frame 3" actually landed — the index was never a stable name for anything, just a snapshot of where something happened to sit a moment ago.

Fixed by routing every tile request off the scan's own ISO 8601 timestamp instead of its position — /frames/:scanTime/tile. A timestamp doesn't shift out from under a request the way a position in a moving window does.

Incident three: the first prune this box had ever run

Nothing had ever deleted a cached render from disk. Ever. The fix — 14-day retention, 100 GB cap, checked every six hours — went out, and its very first prune against a cache that had accumulated for the project's entire history ran automatically on startup: 

60,444,124,338 bytes reclaimed   (59 GB -> 1.5 GB)

Verified two independent ways — the pruner's own accounting against a from-scratch scan of the cache directory — agreeing to three decimal places. That part worked exactly as designed.

What it didn't anticipate: clearing 59 GB in one shot meant every station anyone had recently looked at, including renders from that same morning, went cold simultaneously. A background loop that keeps recently- watched stations warm saw all of them go cold at once and tried to rebuild every one of them at the same time, all competing for a fixed pool of 10 render workers. Load pinned at the pool's ceiling for hours, with a measured 0% cache-hit rate over a 30-minute window — every request a fresh, uncached S3 fetch and render.

Buried inside that legitimate backlog was a real, avoidable multiplier: some individual NEXRAD volumes were independently fetched from S3 3–4 times each, because the in-flight dedup was keyed on the full rendered variant (station + style + filter + floor), not the raw underlying file — every distinct variant of the identical scan triggered its own separate download, even though the source bytes were identical across all of them. A short-lived, key-only dedup map for the raw fetch fixed that specific multiplier. An independent review caught a real bug in the fix before it shipped — the worker pool detaches whatever buffer it's handed for performance, which is safe when every caller owns an exclusive copy and breaks the moment two callers intentionally share one; a one-line buffer copy closed it. Load dropped from a pinned 10.0–11.16 to 0.85 within minutes of the fix landing.

A first-ever prune against a cache that's never been pruned is a fundamentally different event than routine steady-state eviction. Age-based cleanup afterward is gradual by nature and can't cause a stampede; a schema-triggered wipe after months of accumulated history clears everything at once, in one shot, the very first time it runs.

Incident four: corrupted files, straight from the source

Server memory climbed again — 5.2 GB, peaking at 6.2 GB — and one station in particular (KDMX, Des Moines) stopped rendering at all. NOAA had uploaded a run of malformed Level II binary files for that station, an hour straight of them. The parsing library hung on each one until the worker task timeout eventually fired at 90 seconds.

The part that turned a bad hour of uploads into an incident: the background prewarm loop re-fetched the same corrupt files every 60 seconds, forever, because a failed volume preparation wasn't remembered anywhere — each attempt paid the full download-and-hang-and-timeout cost again, stacking overlapping timeout loops and driving memory up with them.

Three fixes landed together:

  • Negative caching — a known-bad volume gets remembered for 15 minutes and fast-rejected in 0 ms on the next attempt, no re-download, no re-hang.
  • Integrity validation before parsing — a minimum radial count, sane radial geometry, a gate-fill-density check, and an azimuth-discontinuity guard, run against the raw bytes before the parser ever gets to them. The fill-density check needed a real second pass: an initial threshold of 50% correctly rejected the byte-shifted corrupt KDMX files but also flagged genuine severe squall lines over Chicago and Davenport as corrupt, because a real MCS can legitimately fill most of a sweep with echo. Recalibrated to 90%, which still catches the 100%-solid corrupt files while leaving real severe weather alone.
  • An honest error instead of a silent hang — a station whose current volume window is corrupt now returns a clear HTTP 503 with a message naming the actual cause, instead of leaving a request to time out with nothing to explain why.

Memory stabilized from a 5.2 GB climb down to a 20–32 MB baseline.

A hang doesn't just fail once — it poisons the in-memory caches around it indefinitely. The never-settling promise from a parser stuck mid-parse stays cached, so every subsequent request for the identical shape silently rejoins the same zombie promise forever, with no new log output to show anything is still wrong. Only a fix that prevents the hang in the first place, not a restart, actually closes this.

A geometry bug that had nothing to do with any of that

Separately, and unrelated to any incident: the NEXRAD interface spec (ICD 2620002P) defines first_gate as the distance to the center of the radar's first range bin. One of the two rendering paths (the wedge/native renderer, the default style) had been treating it as the near edge instead — every gate polygon it drew was shifted half a gate width, 125 meters, too far outward from the radar. Fixed by centering each gate's near and far bounds symmetrically around its true center distance, matching what the other rendering path had been doing correctly the whole time.

What these have in common

Four different subsystems, four different root causes, and the same shape underneath each one: something was allowed to grow without a ceiling (the render cache, the on-disk cache before retention existed), or an identity was assumed stable when the thing underneath it kept moving (the frame index versus its shifting window), or the same expensive work got repeated for the same input because nothing remembered it had already been tried (duplicate S3 fetches, the corrupt-volume retry loop). None of these are exotic bugs. They're the ordinary failure modes of a service that's been running long enough to hit its own edges — the first time a cache is ever actually full, the first time an index actually races its own window, the first time upstream data is actually bad. Every one of them was invisible until it happened for real, under real load, and every one of them is now something the system defends against rather than something it merely hasn't hit yet.
